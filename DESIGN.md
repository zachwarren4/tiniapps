# Microapp Shell Design Brief

## What This Is

Microapp Shell is a personal system for spinning up small, sandboxed, single-purpose microapps. Each microapp is a workspace for one domain of life, such as a Tears of the Kingdom companion, a Spanish-learning workspace, or an astronautics study workspace.

The motivation is isolation: mainstream apps and browsers bleed every context into every other context. This tool should create purpose-built surfaces that do not know about each other.

This is a personal tool for one user on personal infrastructure. No multi-tenancy and no public deployment are part of the design.

## Settled Decisions

- Desktop primary, mobile companion later.
- Desktop shell is Tauri: Rust trusted core, web frontend, OS keychain for credentials.
- Microapps are generated by an LLM from natural language.
- Microapps are stable by default and change only after explicit user instruction.
- Edits regenerate the microapp from an updated `description.md`; code is downstream.
- Each regeneration should become a git commit with the user edit instruction as the commit message.
- Code/config lives in git. User data lives in the shell data directory, scoped by microapp ID, never in the repo.
- In-app LLM calls are explicit button presses, never ambient background behavior.
- The shell owns credentials and brokers every external call. Microapps never receive master credentials.

## Architecture

Three layers:

1. Shell: trusted Tauri process. Holds credentials, runs the generator, brokers capabilities, manages the registry.
2. Microapp runtime: sandboxed webview/iframe. No direct network. Talks to shell through a bridge.
3. Generator: creates `manifest.json`, `description.md`, `app/`, and optional `llm.md` from user descriptions.

## Microapp Repo Shape

```text
manifest.json
description.md
app/
llm.md
.microapp/
```

Clip data and other user data live outside these repos.

## V0 Decisions

### Project Repo Layout

Use a shell repo plus separate microapp repos later. The shell repo can contain reference fixtures under `src/microapps/`, but generated microapps should be independent repos registered by path. This avoids turning the shell into a monorepo of private contexts and makes rollback/history naturally per microapp.

### Capability Vocabulary Principle

A capability should be added when it represents a narrow, auditable boundary between untrusted microapp UI and trusted shell authority. Prefer verbs that describe user-meaningful actions (`web.search`, `clip.save`) over raw platform powers (`http.request`, `fs.write`). Start small, expand only when a reference app needs it, and require capability diffs on regeneration.

### V0 Capabilities

- `web.search`: query search providers through the shell and return normalized results. The first reference app supports source-scoped query transforms for general web, YouTube, Reddit, and Zelda wiki results. If Google Custom Search credentials are present in the shell keychain, they are the preferred generic provider; source APIs and DDG Lite remain fallbacks.
- `reader.preview`: fetch a readable extract (title plus paragraphs) for a single result URL through the shell, so a microapp can render preview text without raw network access.
- `research.gather`: higher-level capability that expands a natural-language query into TOTK-scoped per-source searches, gathers a capped corpus of `{ source, title, url, snippet, preview }` entries, and returns it alongside the expanded queries the shell actually used. Reuses the `web.search` provider chain and `reader.preview` extractors under the hood.
- `llm.complete`: explicit one-shot LLM completion through the shell using the shell-held Anthropic key.
- `browser.open`: open an `http` or `https` result URL in a shell-owned Tauri webview window for the active microapp context.

For v0, isolation is mainly contextual: the goal is to keep a microapp's searches, result browsing, and summaries in its own surface instead of the general browser. Credentials and shell APIs still stay behind the broker.

The generic pattern to prove is provider indirection: microapps ask for a source like `reddit` or `youtube`, while the shell decides whether that means Google Custom Search, a native API, a static index, or a fallback web search.

Deferred: `external.fetch`, `reader.extract`, `clip.save`, `clip.search`, `storage.get`, `storage.set`, `gmail.search`, `gmail.read`, `youtube.search`.

### Clip Store Direction

Use one SQLite database owned by the shell with `microapp_id` columns, not a SQLite file per microapp. The shell is already the trust boundary and registry owner, and one database makes backups, migrations, and cross-version schema management simpler. Enforce isolation in the broker API, not by exposing SQL or file paths to microapps.

A first `clips` table should likely include:

- `id`
- `microapp_id`
- `source_url`
- `source_title`
- `content`
- `content_type`
- `created_at`
- `updated_at`
- `user_notes`
- `tags_json`
- `metadata_json`

No clip store is implemented in this first scaffold.
